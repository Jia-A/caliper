# Changelog

## Unreleased

### Added

- **Prompt sizes in the server block.** When a marked visit's record has a `prompt` field (caliper-timings 0.2.0's `run.prompt(messages)`), the "Inside the server" block shows each message's role and UTF-8 bytes, with its share of the measured total, and the total: `prompt sizes (marked visit 1) — UTF-8 bytes of each message's text as your app passed it to run.prompt(); not tokens`. From the first visit that recorded one. A message with no size shows `–` and "not measured", and the total says how many were measured. Without any, `prompt sizes: none recorded (needs caliper-timings 0.2.0 or later, and run.prompt(messages) before the model call)`. A `prompt` field that isn't the expected shape, or has a role that isn't a lowercase name of up to 32 letters or `_` (or `"?"`), isn't shown (`prompt sizes ? — marked visit <i>: <why>`) and the visit's timings stay. The HTML report shows the same rows as a table under the marks and spans. Tested with `npm run test:serverblock` and `npm run test:marked` (fake wrapper records), and end to end with caliper-timings itself on a local app with `npm run test:prompt`: a marker put in every part of the prompt never reaches the terminal output or the HTML report.
- **Caliper asks when it isn't sure which request is the AI reply.** On the first run that names a winner, Caliper counts the output changes from the winner's first body byte on. The winner must explain at least 95% of them, and no other request's bytes may come ≤ 250 ms before 50% or more of them. Both are Caliper's own thresholds, measured on the fixtures: 100% and 0% where one stream fills the output; 54% and 92% for two streams taking turns; and 94–98% won by a 50 ms heartbeat on a typewriter page, whose reply bytes came ≤ 250 ms before 65–67% of the changes. Otherwise Caliper lists up to 3 candidates (`1) POST /generate — 30 of 87 changes (34%)`). In an interactive terminal it waits 2 minutes for a number, and that request (method and path) is used for every timed run and marked visit after it. With no answer, or with no terminal (CI, piped), or after Ctrl-C at the question, it stops with no more runs and no report: `Too close to choose. Rerun with --request "…" or --request "…"`. Every run shows the chosen request's share, with the thresholds, in the terminal and the report (`share: 13 of 13 output changes from its first body byte (100%) — …`). Only the first run is checked. Tested with `npm run test:ambiguous` (two streams taking turns, a tie, a typewriter page next to a heartbeat, no terminal, no answer in time, the answer reaching the marked visit; the terminal runs need python3).
- **Test for the missing-browser instruction** (`npm run test:browser`): with Playwright pointed at an empty browsers folder, `caliper audit` and `caliper login` print `Chromium for Playwright isn't installed. Run: npx playwright install chromium` instead of Playwright's box. Checked against Playwright 1.64.1, the current release, whose error still starts `browserType.launch: Executable doesn't exist at …`.

- **The HTML report is on by default.** Every audit that finishes writes `caliper-report.html` in the current directory. The last line is `report: wrote <path>` or `report: overwrote <path>`. Use `--report <path>` for another path and `--no-report` for none (both together is an error). An early exit ends with `no report written: every run failed to load` or `no report written: the audit stopped on the error below`. Tested with `npm run test:auth`.
- **Report restructured**, top to bottom:
  - the verdict: the median wait for the first word, then each side's top hint with how many times its limit, or "nothing over its limit";
  - one bar per side: the browser's warm run nearest the median, and the server's marked visit nearest the median, with overlapping spans on separate rows. Over-limit segments are drawn in a warning colour and labelled "over";
  - where to look, under each bar;
  - the checks;
  - a collapsed Details with the tiles, the per-run timeline, the Data table, request matching and clock check, and the server marks table.
  The terminal prints the same verdict lines under the summary. Tested with `npm run test:hints` and `npm run test:marked`.

- **Things to check when a `--step` or `--measure` button doesn't appear.** The error stays the same and is followed by:
  - the visible buttons' accessible names at the timeout (at most 15, trimmed, deduped), then `None matched /<pattern>/i.`;
  - with `--auth`, a line when a cookie in that file for the audited site has expired, with its date and the `caliper login` command (nothing about login otherwise);
  - without `--auth`, a line that no saved login was used.
  Timed runs only. Tested with `npm run test:auth` and `npm run test:loadhints`.
- **Where to look.** Each segment's median is compared with a limit for its layer: 200 ms for click → request sent, 600 ms for headers received, 450 ms for model call → first bytes sent, and 100 ms for everything else, including every app-named span. Every segment over its limit is listed, in two separate lists that are never compared: browser (warm runs) and server (marked visits). The one furthest over its own limit (median ÷ limit) comes first, then by more runs over on a tie. It gets the evidence (`postgres: median 532 ms — 5.3× its 100 ms limit, in 3 of 3 marked visits; …`, with that side's share), its basis, things to check and "Caliper sees timings, not your code — these are common causes, not a diagnosis." The rest get one line each. App-named spans get the same generic text whatever their name, and "unattributed" is never hinted. Browser hints end with "Learn more" links (clickable in the HTML report); the model and app-named spans have none. Shown in the terminal and the HTML report. README: "Why these limits?". Tested with `npm run test:hints` and `npm run test:marked`.

- **Server timings in the HTML report.** With `--server-timings` and `--report`, the report has an "Inside the server" section: the pre-check, visit and `?` lines as printed, then the block as a table (one column per visit, then min · median · max), the no-span lines, the Workers and first-bytes notes, and the server's problems. Its numbers are the terminal's; one line says they come from separate runs on the server's clock and are never added to the browser timings. Without `--server-timings` there's no section. Mark names and problems from the server are HTML-escaped. Tested with `npm run test:marked` and `npm run test:serverblock`.

### Changed

- **`--request` also takes `"METHOD /path"`** (`--request "POST /generate"`): that method and exactly that path, on any origin, with any query string. Anything else is a case-insensitive regex on the URL, as before.
- **A `--request` no request matches fails that run, not the whole audit.** The run is reported as `AI request not identified` with `no request matches --request "…" (seen: …)`, and the other runs go on. The Stop, double-send and canary checks still stop the audit with `No request matching --request "…"`.
- **A `--request` or an answer that 2 or more requests match fails that run** instead of using the first match. The run is reported as `AI request not identified` with every match: `2 requests match --request "POST /marked/reply": POST …/marked/reply?…&kind=ping, POST …/marked/reply?…. Caliper doesn't guess which one is the AI reply: rerun with a --request regex that matches only one.` Tested with `--request "METHOD /path"` and a regex `--request` on a page that sends a JSON ping and then the reply to the same path; after an answer it's the same check, not tested separately. The Stop, double-send and canary checks still use the first match.
- **An answer that later runs can't find says why.** When the request you chose isn't in a later run (its path changes per run, e.g. `/chat/abc123/reply`), that run's line ends with `If its path changes per run, rerun with --request and a regex on the URL (e.g. --request "/chat/[^/]+/reply" for /chat/abc123/reply).` Tested with `npm run test:ambiguous`.
- **Known limit, now tested:** only the first run is checked for a close call. When run 1 is clear, later runs still pick by timing on their own, and can pick another request: on the test page, runs 2 and 3 pick a status stream (share 7 of 12, 58%) over the reply run 1 picked. Their share line shows it. Later runs aren't locked to run 1's request, so the server-timings wildcard key (a path part that differs between runs) keeps working.
- **A tie between two requests on the first run is asked about** (its share is 50% at most), instead of being reported as not identified. Later runs still report a tie as not identified.

- **Plainer labels** (display only; the record's field names and the protocol are unchanged):
  - "model: first chunk" → "server: first bytes sent". It's the server's first write to the browser, so a line under the server block now says: `first bytes sent = the server's first write to the browser. If your app writes anything before the model's reply (a heartbeat, an envelope), this is that write.` It appears when a visit recorded `firstChunk`. The row's "(at the server, not the browser)" note is gone, since the label says it.
  - "model: sent → first chunk" → "model call → first bytes sent".
  - The browser segment "request → first byte" → "browser: response headers received", which is what it measures (Playwright's `responseStart`).
  - "first byte → done" → "headers → done", and "first byte → first paint" → "headers → first paint": they start when the headers arrive.
  - The clock check now reads `response headers within <n> ms of Resource Timing`, or `n/a (Resource Timing hides the response headers time without Timing-Allow-Origin)`.
  - The terminal's label column is wider to fit them: 36 characters in each run's rows, 32 in the server block.
- **Data table** in the report: one row per segment and one column per run, so it fits a narrow screen. Its headers wrap, and it scrolls inside its own box rather than being cut off. Request matching and the clock check are now a list per run.
- **HTML server section:** the table comes first. The pre-check and visit lines are in a collapsed "Run details", which is open when no visit succeeded, since then those lines are the only explanation. The terminal is unchanged.

## 0.4.0 — 2026-11-04

### Added

- **`--server-timings <origin>`: marked visit (step 1 of server timings).** With `CALIPER_TOKEN` set in the environment, one extra page load after the timed runs stamps the AI request with `x-caliper-run` (a fresh id, printed) and `x-caliper-token` (never printed). The request stamped is the first one after the click that matches the key built from each run's AI request: method, origin and path, with the query string dropped and path segments that differ between runs as one-segment wildcards. Nothing else is touched, and the timed runs are never stamped.
- The token only goes to the named origin: the key's origin must equal it exactly, so a subdomain, a longer host or a longer port is not a match. Otherwise nothing is sent, and the line says where the request went.
- When Caliper can't tell, it reports `Server timings ? — <reason>` instead. That happens when a run was inconclusive, when the runs disagree on method, origin or number of path segments, or when 0 or 2+ requests matched during the marked visit. It also happens when the marked visit's AI request wasn't the stamped one. With `--runs 1` the line says changing path parts can't be detected.
- Without `CALIPER_TOKEN`, `--server-timings` is an error, as is a value that isn't an `http(s)` origin. `CALIPER_TOKEN` alone does nothing.
- **Token pre-check.** Before the marked visit, Caliper asks `<origin>/__caliper/timings/caliper.precheck` (a deliberately malformed id, so it can never reach a record) with `Authorization: Bearer <token>`, and doesn't follow redirects. A `400` goes ahead. `401` (token rejected), `404` (no wrapper, or `CALIPER_TOKEN` not set on the server), any other status, or a network error skip the marked visit. Either way one `pre-check:` line says what it got, for example `Server timings — pre-check: feature on, token accepted (400 on caliper.precheck)` or `Server timings ? — pre-check: token rejected (401 on caliper.precheck): wrong, expired or rotated; no marked visit.`
- **Server record printed.** After a stamped run whose AI request was the stamped one, Caliper fetches `<origin>/__caliper/timings/<run id>`. It prints an "Inside the server (from 1 marked run)" block: each recorded mark in ms after the request arrived, plus spans when both of their marks are in the record (see "Spans are app-chosen" below). A note that Workers time waits only appears when the record has `"runtime": "workers"`, and not otherwise. Nothing that wasn't recorded is shown or computed, and the numbers are never mixed into the user-timing summary. A missing record (`404`), another status, or a record of the wrong shape prints `Server timings ? — <reason>`. Terminal only.
- **`--server-runs <n>`: several marked visits** (default 3, 1 to 10, only with `--server-timings`; anything else is an error before any run). Before any run, Caliper prints `This audit triggers the AI feature up to <runs + n> times for timing (<runs> timed + <n> marked).` It counts triggers, not requests: the endpoint isn't known until the runs pick it, and `--stop`, `--double` and `--canary` aren't counted. The token pre-check runs once. Then each visit gets a fresh run id, with the same key and rules. A visit that fails prints `Server timings ? — marked visit <i> of <n>: <reason>` and is left out. The block is now headed "Inside the server (from <k> of <n> marked runs)" and shows each visit's value per mark and span, then min · median · max across the visits that recorded it (just the value with one visit). Spans are computed inside each visit, then summarised. If no visit succeeds: `Server timings ? — 0 of <n> marked visits succeeded`. The marked visits stay out of the browser summary.
- **Spans are app-chosen ([caliper-timings SPEC v1](https://github.com/Jia-A/caliper/blob/main/packages/timings/SPEC.md#marks)).**
  - **Marks:** every recorded mark is shown under its own name, in the order they happened. The reserved `modelCallSent` and `firstChunk` keep their labels.
  - **Spans:** each `<name>Start` / `<name>End` pair is a span called `<name>`, replacing the fixed "database wait". Quill's `postgresStart`/`postgresEnd` show as `postgres`. "model: sent → first chunk" stays.
  - **No span:** when a pair is missing a mark, or its End is before its Start, there's no span, and one line per pair says why. With several visits, that line says how many visits had no span and which ones when not all, then the reason once if it's the same, else per visit.
  - **Problems the server reports** (the record's new `problems` list, for example a mark name the wrapper skipped) are printed last, once each, with control characters escaped and anything past 200 characters cut. A `problems` that isn't a list of strings makes that record unusable, with the reason. Unit-tested on fixed records (`npm run test:serverblock`).
  - **Workers note:** it now reads `Workers time waits only — a span with only computation inside (no I/O) can read 0 ms.`
- **Failed page loads no longer cancel the marked visits.** If at least one timed run loaded, the key comes from the runs that loaded (same rules), and every marked-visit line says so: `(key from <k> of <n> runs; run <i> failed to load)`, plus the one-run note when k = 1. A run whose AI request wasn't identified still blocks the key. With no run loaded, nothing changes.
- **Things to check after a failed page load.** Each "page failed to load" line, in the timed runs and in the marked visits (`Server timings ? — marked visit <i> of <n>: page failed to load: …`, which used to say "didn't get to the click"), is followed by candidates for that error type, then `Rerun to try again.` Playwright's navigation timeout: your network connection · whether `<origin>` is up · `--timeout (now <ms>)`. `net::ERR_CONNECTION_REFUSED`: whether `<origin>` is up · the port in the URL. `net::ERR_TIMED_OUT`: your network connection · whether `<origin>` is up (no `--timeout`, since that timeout is Chromium's). Any other error gets only the rerun line. The first two were reproduced on local fixtures. `net::ERR_TIMED_OUT` was seen in a real run (Oct 29), not reproduced locally; it's unit-tested with that run's exact error line (`npm run test:loadhints`).
- Known limits: tested on local fixtures only (click and chat runs, with and without `--request`; several visits in click runs only). The Stop, double-send and canary checks don't print things to check yet. It hasn't been tried on a real server, a cross-origin API behind a CORS preflight, or with `--stop`, `--double` or `--canary`. Not in the HTML report yet.
- Test: `npm run test:marked`.

### Changed

- **`--auth` is optional for `caliper audit`.** Without it there's no saved session, the same as an empty session file, and Caliper prints `No --auth given: running without a saved session.` An `auth.json` in the current directory is no longer loaded unless you pass `--auth auth.json`. With `--auth`, nothing changes: the file is loaded, and a path with no file is an error before any run. `caliper login` still saves to `auth.json` by default. Tested with `npm run test:auth`.

## 0.3.0 — 2026-10-27 — tested on two real apps: a Gradio Space and a custom-built chat app (PDFSimpli)

### Added

- **Chat-style triggers: `--input <selector>` and `--prompt <text>`.** Caliper types the prompt into the input and sends it with the `--measure` button, or Enter when there's no `--measure`. The click or keydown starts the timer.
- **`--output` may be a container** (for example the message list) with `--input`. Caliper watches it for added nodes and text changes. Your own message (an added node whose trimmed text equals the prompt) doesn't count, and the first word is the container's first change at or after the AI request's first body byte. Earlier changes, such as a "Thinking…" placeholder, are listed as pre-reply changes in the terminal and the report's new "Before the reply" table, and are never timed. Done uses the same settle window as before.
- Test: `npm run test:chat` (chat-style run against a local fixture with a placeholder and an SSE reply), and a chat case in `npm run test:nostore`.
- **`--measure-selector <css>`: click by CSS selector.** For icon-only buttons (an `<svg>` with no text or `aria-label`) that `--measure` can't find by name. It must match exactly one element: 0 or more than one stops the audit with an error that gives the count. The clicked element (tag, id, and the first 60 characters of its `aria-label` or text) is printed before each run. Tested in click runs and with `--input`/`--prompt` only, not yet with `--stop`, `--double` or `--canary`. Passing it together with `--measure` is an error. `--measure` still matches by name only. The report shows the selector under "Measured button" or "Sent with".
- Test: `npm run test:selector` (an icon-only send button where Enter doesn't send, in click and chat mode, plus the 0-match, 2-match and both-flags errors).

### Changed

- **The AI request is picked by time correlation, for clicks and chat sends alike.** The old scoring (longest, last to finish before first paint, …) only rewarded requests that had already finished, so on a queue-style app (a Gradio Space) it picked a 230 ms JSON side-call and reported a 281 ms first word for a reply that took far longer. Now every request sent since the trigger is a candidate, including streams still open, or opened only after, when the output starts changing. Caliper watches until they've all ended and the output has been quiet for `--settle-ms`, counts each output change toward the request whose body bytes (CDP `dataReceived`) arrived last within 250 ms before it, and picks the request that explains the most changes. It must be the unique top with at least one; a tie, or none, is reported as "AI request not identified, timing inconclusive", with no number, and the run is left out of the medians. Matched on timing, never on text.
- **First word** is the first output change at or after the chosen request's first body byte, for click runs too. **Done** is never earlier than that request's last body byte or end.
- Click runs list pre-reply changes when there are any. On a page whose output simply fills in from one stream (Quill), the numbers match 0.2.1 within run-to-run noise; only the "chosen from" line reads differently.
- The Stop and double-send checks still pick their request with the old scoring.
- A page whose output no request explains (for example, generated in the page itself) is now inconclusive instead of timed. Its run waits up to `--timeout` for a request to explain a change.
- Test: `npm run test:sidecall` (a fast side-call that renders a placeholder, next to a slow streamed reply; and a page no request explains).
- `--stop`, `--double` and `--canary` can't be combined with `--input` yet.

## 0.2.1 — 2026-10-26

### Fixed

- **No more hang on streams that end `net::ERR_ABORTED` after the full body.** Chromium ends a streamed response sent with `Cache-Control: no-store` that way once the page has read all of it, and Playwright's `response.finished()` then never settles, so the run waited out `--timeout` and the audit failed. Caliper now waits for the request to finish *or* fail, bounded by what's left of `--timeout` from the click. A request that ended `ERR_ABORTED` counts as finished when the body bytes Chrome received (CDP) match the body the page's Resource Timing entry recorded. It's labelled "ended ERR_ABORTED after full body — treated as finished" in the terminal and the report. A request aborted mid-body is noted as "ended net::ERR_ABORTED; full body not confirmed" instead (the same note when the body can't be confirmed, e.g. cross-origin without `Timing-Allow-Origin`).
- Test: `npm run test:nostore` (a no-store stream read in full, and one the page really aborts).

## 0.2.0 — 2026-10-26

### Added

- **Streaming verdict.** Each run reports click → first word, click → done and the streaming span (first word → last change), and flags answers that don't stream. `--settle-ms` sets when the output counts as done.
- **`--stop <text>`: Stop check.** One extra run clicks Stop mid-stream and checks that the output stops, the browser aborts the AI request, and the request never ends normally.
- **`--double`: double-send check.** One extra run clicks the measured button again mid-stream and reports whether the second click was prevented or ignored, or whether the previous request was cancelled, left running (paid twice), or its answer left on screen.
- **`--canary` / `--canary-input <selector>`: canary image check.** Plants a markdown-image instruction and reports whether the page turned the model's output into an image request, whether CSP blocked it, or whether the page showed it as text. Image requests are answered locally, so nothing leaves the machine.
- **`--csp`: CSP check** (on by default with `--canary`). Reads the page's Content-Security-Policy from response headers and `<meta>` tags and reports where images may load from, combining all enforced policies. Report-Only is reported separately.
- **`Fix:` lines** under every failing or warning verdict, in the terminal and the HTML report.
- **Summary block**: one line per check (✓ pass, ⚠ warning, ✗ fail, ? inconclusive) at the end of the terminal output and at the top of the HTML report.
- Tests: `npm run test:csp` (CSP parser unit tests) and `npm run test:canary` (canary check against a local fixture, with and without CSP).

### Changed

- A timed run whose page fails to load (for example `net::ERR_TIMED_OUT`) no longer stops the audit. It's reported as "page failed to load" and left out of the medians, and the summary says how many runs were used. If every run fails, Caliper prints "Inconclusive — page failed to load" and exits.
